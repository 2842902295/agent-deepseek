# Standards DB — 标准查询与正文阅读规范

两类任务：**问数**（查元数据、做统计）和**正文查阅**（读章节、找内容）。
无论哪类，遇到模糊的主题式需求（「帮我找XX相关的标准」），先看「先对齐再动手」一节，不要拿关键词直接开搜。

## 能力来源（重要前提）

本文涉及的数据工具**全部由「标准数据集」提供（经 MCP 接入）**，不是内置能力——
用户添加/启用对应数据集后，相应工具才会出现在你的工具列表中：

| 能力 | 需要的数据集 | 对应工具 |
|---|---|---|
| 问数 / 全量统计 / 表结构探索 | 标准元数据集 | `standard_query` / `standard_tables` / `standard_schema` / `search_standards` / `vector_search_standards_ob` |
| 正文查阅 / 章节语义定位 | 条款集 | `get_standard_chapters` / `vector_search_chapters` / `vector_compare_standards` |
| 术语检索 | 术语集 | `search_terms` / `search_terms_vector` |

工具列表里找不到相应工具 = 用户还没启用对应数据集：如实告知并引导启用，入口有二：
① 打开**侧边栏的「数据集」**，添加/启用对应数据集；
② 点**输入框里的「+」号 → 「数据集」**，找到对应数据集拨开关启用（还没添加过就点
底部「添加数据集」进数据集管理页添加）。
不要假装已查询、不要编造数据，更不要试图用 shell 直连数据库。

## 先对齐再动手（模糊主题式需求必读，重要）

用户说「帮我找『复合材料』相关的标准」「有没有无人机检测方面的标准」这类**模糊主题式需求**时，**禁止拿原始关键词直接就去搜标准名称**——先花一轮对话把检索口径对齐。需要澄清的判断依据：

- **范围宽窄**：宽泛联想（周边材料 / 工艺 / 测试方法 / 应用场景沾边的标准都要）还是严格聚焦（标准对象直接就是该主题本身）？
- **关注角度**：只看标准名称与适用范围做筛选，还是要深入到具体技术内容（术语、指标、试验方法——那就要搜章节条款）？
- **过滤条件**：只要国家标准，还是行业标准也要？要不要国际标准（ISO/IEC——注意它们只有元数据和英文名，没有正文）？有没有特定行业 / 领域 / 年份限制？现行有效性默认按「只查现行」执行（口径见场景一「重要事实」），不必专门问，呈现结果时注明即可。
- **用途**：编制文件参考、产品合规、调研综述？用途不同，推荐侧重不同（合规偏强制性现行标准，调研要覆盖面广）。

提问要求：

1. **一次问完**：一条消息列出 1~3 个关键决策点，每个都附上你的推荐默认值（如：「没有特殊要求的话，我按『主题强相关 + 现行有效 + 国标行标都含』来找，可以吗？」）。用户确认或修正后按定下的口径执行，**不要挤牙膏式多轮追问**。
2. **需求已明确时不问**：点名了标准编号、给了精确字段条件（某单位起草 / 某年发布 / 某状态）、指定章节内容、明确统计口径的，直接执行。
3. **用户催急时不问**（「先查一下」「直接给我结果」）：选合理的宽口径先搜，呈现结果时说明所用口径，并告知可以怎么收窄或放宽。

**动手前先充分理解这个领域，目标是找全又找准。** 用户要找某领域的标准时，期望是「尽量齐全、又尽量准确」。为此：

1. **先理解领域再检索**：主题词（如「复合材料」）只是入口。动手检索前，先用你的领域知识把该领域拆解一遍——核心对象是什么、涉及哪些相关材料/原料、哪些工艺与制造方法、哪些测试/检验方法、哪些典型应用场景、有哪些关联设备与配套件。拆解出多少个子方向、用户实际可能关心哪几个，决定了你组织几路 query、召回量开多大。
2. **先摸清库的整体情况（总览，不是单关键词数数）**：宽领域检索前，先用 `standard_query` 把该领域在库中的整体面貌盘出来——
   - **存量**：按主题关键词及相关词在名称/适用范围中粗计，这个领域大概有多少条；
   - **结构分布**：对命中的候选集按性质（强制性/推荐性）、编号前缀（国标/行标）、年份、行业、归口单位等维度做 GROUP BY 统计，看集中在哪、什么形态；
   - 由此形成「有多少、什么样、集中在哪」的立体认识：召回量怎么定有依据，query 往核心方向组织，交付时还能反向校验齐全度（最终清单与存量明显不符时，主动回查原因）。
3. **召回规模跟着领域走**：`top_k` / `limit` 不是写死的数——宽领域（子方向多、相关标准多）就传更大的值、按子方向多路组织 query 分别召回再合并去重；窄领域小值即可。**宁可多召回再认真甄别，不要一开始就漏一大片**。
4. **召回后靠甄别保证准**：对召回结果逐条判断相关度再组呈现（见下方「结果呈现前先甄别」与场景一「多通道结果合并与甄别纪律」）。

对齐后按口径选用对应策略执行：

- **宽召回**：语义检索（`vector_search_standards_ob` / `vector_search_chapters`），按上一步拆出的子方向组织多路 query 召回；`top_k` 按领域宽窄定（宽领域放大），`min_score` 适当调低（弱相关也想看时）。
- **窄精确**：`search_standards` 关键词过滤，或 `standard_query` 按字段写精确 SQL。
- 两种可组合：先语义广召回（`vector_search_standards_ob` 返回已自带该标准的全部元数据字段，一般无需再补；确缺个别字段时用 `WHERE standard_no IN (...)` 按编号批量取）、自主甄别收窄。**多通道结果的合并与甄别规则见场景一「多通道结果合并与甄别纪律」**。

结果呈现前自己先做一轮甄别：结合标准名称与**适用范围**判断相关度（不要只看名称是否含关键词），按主题相关度 / 类型 / 行业归组去重后再呈现，不要原样倾倒检索列表。

## 场景一：问数

**唯一数据源：`standard_base_info` 表**——所有标准元数据查询必须且只能从此表获取，禁止查 `standard_cache_*` 或其他表。

**重要事实：库内构成与默认口径（务必先读）。** 库内三类标准，**没有团体标准**：

- **国家标准**：`standard_no` 前缀 GB / GB/T / GB/Z；中文名、适用范围、正文基本齐全。
- **行业标准**：`standard_no` 前缀为行业代号（如 JB/T、YD/T、HG/T、QB/T、YS/T、FZ/T、SJ/T、JC/T、HB、WJ/T 等）；特征同国标。
- **国际标准**：`std_type` = ISO / IEC，编号形如 `ISO 10377:2013`；**无中文名（只有英文名 `ename`）、无适用范围、无正文**，仅元数据。

注意：国内标准（国标 + 行标）的 `std_type` 列**为空**，国标/行标靠 `standard_no` 前缀区分；`std_type` 只在国际标准上取 ISO / IEC。

**状态（state）与默认口径：**

- 国内标准：绝大多数为「现行」，另有少量「废止」「尚未实施」或状态为空。
- 国际标准：英文状态枚举——`PUBLISHED`（现行）/ `WITHDRAWN`（废止）/ `REVISED`（修订中）/ `REPLACED`（被替代）/ `DRAFT`（草案）/ `IN_DEVELOPMENT`（制定中），其中非现行占比不小。
- **默认口径**：用户找标准未特别说明时，国内标准加 `state = '现行'`，国际标准加 `state = 'PUBLISHED'`；用户明确要废止 / 被替代 / 草案时才放开对应状态。呈现结果时注明所用口径。

**检索通道能力边界：**

- 语义检索（`vector_search_standards_ob`）**只覆盖国内标准**（向量库只收录有中文名的记录）；找国际标准用 `search_standards`（关键词匹配英文名）或 `standard_query`（编号前缀 / `ename LIKE`）。
- 国际标准无正文：用户要读 ISO/IEC 正文时，如实告知库中只有其元数据（编号 / 英文名 / 状态），不要反复尝试取章节。

字段已内置如下，**禁止对这张表再调 standard_tables / standard_schema / read_skill**，直接用 `standard_query` 写 SQL。

### 常见查询模式

- 按编号精确查：`WHERE standard_no = 'GB/T XXXX-YYYY'`
- 模糊找标准：主题式需求先按「先对齐再动手」确认口径并拆解领域；检索优先 `vector_search_standards_ob(query)` 语义召回（`top_k` 按领域宽窄自定，无固定上限；**返回已自带该标准的全部元数据字段，直接可用**），结合名称与 `use_range` 判断相关度，再用编号精确取详情。**语义检索只覆盖国内标准**——找国际标准（ISO/IEC）见下一条
- 找国际标准：国际标准没有中文名，**语义检索覆盖不到**（向量库只收中文名）；用 `search_standards(keyword=英文关键词)` 匹配英文名，或 `standard_query` 按编号前缀 `standard_no LIKE 'ISO%'`（或 'IEC%'）/ `ename LIKE '%关键词%'`，默认口径记得带 `state = 'PUBLISHED'`
- 统计分析（含全量统计：按年份/行业/性质/状态/起草单位等维度的数量、分布、覆盖面）：用 `standard_query` 执行 SQL GROUP BY + COUNT，结合 `LIMIT`；**统计结果必须调用 `create_chart` 生成图表**（bar/pie/line），并将工具返回的 ` ```chart ... ``` ` 文本**原文完整复制**到回复正文中，不得省略

### SQL 纪律

- 所有 SQL 一律经 `standard_query` 执行（只读安全门：仅单条 SELECT、仅 standard_ 前缀表）；尽量带 `LIMIT`（未写会自动补 LIMIT 2000；需要更多行时显式写更大的 LIMIT 即可）
- 回复用户时只讲业务语言：表名、字段名、SQL、过滤条件（如 deleted=0）一律不出现在回复里，也不写「数据来源」附录（见系统提示「回复中禁止暴露技术实现细节」）
- 元数据只查 `standard_base_info`，并加 `deleted = 0` 过滤软删除；`standard_cache_*` 系列表禁止查询
- 统计正文情况（哪些标准有正文、章节数量等）可直查 `standard_jgh_pdf` / `standard_jgh_pdf_chapter`，两表用 `main_task_id` 关联（先按 standard_no 在 standard_jgh_pdf 取 main_task_id）；读取正文内容本身走场景二

### 多通道结果合并与甄别纪律（重点）

同一批标准经由多个通道获取（语义召回 / 关键词 LIKE / 字段条件 SQL）时，最终清单应该是**对各路结果自主甄别后的合并**。历史事故：语义检索召回了 80 条候选，随后为了"补齐归口/起草单位字段"转用 SQL 关键词匹配兜底取数，最终交付的 135 条主体变成了关键词命中结果，语义召回的 80 条候选大部分丢了——**这不是「甄别」，是「换通道」**，必须杜绝。

正确姿势（自主判断，不是机械执行）：

- **留/弃的依据是相关度，不是字段齐不齐**：对每条语义召回候选，自己判断与用户主题是否相关（看 `cosine_score`、适用范围、标准名称，结合你的领域常识）。相关的留，确属不相关的弃，拿不准的标注出来交由用户定夺。**不要求把召回结果一条不落地全进最终清单**——召回的价值正在于你替用户做了他做不了的初筛。
- **补字段的正确方式只有按编号批量取**：`SELECT ... WHERE standard_no IN (...)`（`vector_search_standards_ob` 返回已自带全部元数据字段，一般无需再补）。**严禁为"补字段"改道关键词 LIKE 重新搜一遍**——关键词命中既不完整也不聚焦，会污染已有的召回判断。
- **关键词 LIKE 只作补充召回**：补语义检索漏掉的精确命中（编号前缀、确切的起草单位名称等），补充结果与语义结果合并去重。
- **丢弃要能说出理由**：剔除得多（比如召回 80 条只留 30 条）时，向用户交代你的筛选口径（如"其余多为工艺类，与所问的材料要求关系不大，已剔除"），让用户能判断要不要放宽找回。
- **输出前自查**：最终清单里的每一条都是凭判断留下的吗？有没有哪一路的结果是因为"另一路取数更省事"被整体放弃的？若有，修正后再交付。

## 场景二：正文查阅

用户要看某标准正文内容时，**怎么快怎么来，能一步到位就不要分两步**：

1. **用户点名了章节**（说出章节号或章节名，如"第4章"、"范围"、"规范性引用文件"）：
   直接 `get_standard_chapters(standard_no, title_no_prefix=...)` 一步取回正文，**不要先取目录**；
   `title_no_prefix` 章节号和章节名都接受，多章用逗号分隔（如 `"4,5,6"` 或 `"范围,规范性引用文件"`）。
   传父章节（如 `"4"`/`"附录A"`）会自动取回该章及其全部子章节。不少标准的父章节自身正文为空、内容都在子章节里，**单个章节正文为空不代表标准缺内容**。
   若未命中，返回结果会自动附带完整目录（toc 字段），据此改选后重试即可，不要再单独调 toc_only。
2. **用户没点名章节**：先 `get_standard_chapters(standard_no, toc_only=True)` 拿目录，了解章节结构和各章字数，再用 `title_no_prefix` 定向获取正文。
3. 章节内的表格/公式/图片：`get_standard_chapters` 默认已随正文一并还原、附在各章 `media` 字段——table/formula 条目的 `content` 是解析好的 HTML/LaTeX，**就是数据本身，直接用**；`path` 是截图/插图，仅在展示给用户时用。**不要再额外调工具**；遇到"见表X"这类跨章引用，直接 `keyword="表X"` 读取该表所在章节即可。
4. 用户问题模糊（未指定章节号、从目录也难判断）时，先用 `vector_search_chapters(query, scope_standard_nos=standard_no)` 语义定位章节，再取正文。
5. 仅当不带过滤条件的整体查询返回空（total=0、toc 也没有任何章节）时，才告知用户该标准暂无电子正文；**严禁因个别章节正文为空就断言标准不存在或没有内容**。
6. **国际标准（ISO/IEC）一律没有正文**：库中只收录其元数据（编号 / 英文名 / 状态）。用户要读 ISO/IEC 正文时，直接如实告知，不要反复尝试 `get_standard_chapters`。

## 图片展示（重要）

章节内容中经常包含图片（示意图、原理图、结构图等），这些图片**必须展示出来**，不能只描述。

**图片登记步骤（每张需要展示的图都要做）：**
1. 在章节 `media` 字段里找到对应条目的 `path`（如 `images/xxx.jpg`）：`type == "image"` 条目是插图，table/formula 条目的 path 是截图
2. 立即调 `register_artifact(name="图X-标题.jpg", artifact_type="image", relative_path="images/xxx.jpg")`
3. 在回答正文中对应位置插入 `[artifact:<ID>]` 占位符（独占一行，前后空行）

注意：`path` 字段已是 workspace 内的相对路径，直接传给 `register_artifact` 的 `relative_path` 参数。

回答时直接呈现章节内容，**不要把整个 word 字段原文抛出**，要提炼关键信息后组织回答，图片按位置穿插展示。

## 图片/表格阅读纪律

- `media` 里 table/formula 条目的 `content` 是解析好的 HTML/LaTeX，**就是数据本身，直接读文本取值**；`path` 截图仅用于展示给用户，不要读图取数
- `type=image` 插图条目：按系统提示中「看图」章节的方式查看（原生视觉模型能直接看到已内联在工具结果里的图片；纯文本模型调 `vision_inspect(file, question)`，file 用 workspace 相对路径）
- **严禁**用 `read_file` 读取图片文件（文本模型看不见，base64 还会永久占用大量上下文）；**严禁**用 shell（python / PIL / pytesseract 等）对图片做 OCR 或解码尝试，第一次失败就停止
- 图片占用上下文：只查看确实需要看的图，并把关键信息及时提炼成文字

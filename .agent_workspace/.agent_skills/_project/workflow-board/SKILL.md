# 工作流画板：板型方法论（workflow-board）

> **本 skill 是 project-bound**——直接调用本项目 qa_agent 挂载的 read_workflow / edit_workflow_board，无法跨项目移植。规范见 `_project/README.md`。
> 画板页的基础协作规则（板子为先、两种连线、卡片格式、附件上板等）已随消息注入，这里不重复。本文只解决一件事：**怎么把板布成项目的结构图，而不是做事的流水账**。

## 为什么板会变成流水账

模型的叙事本能是「按发生顺序讲」：接到任务 → 先调研 → 再整理 → 再核查 → 最后定稿。照这个本能播种，板上就是一条单链：

```
开始 → 明确需求 → 查资料 → 整理结果 → 核查 → 定稿 → 结束
```

这是**做事的过程**，不是**项目的结构**。后果：

- 用户打开板看到的是「你先做了什么后做了什么」，不是「这个项目由哪几部分组成」；
- 项目越推进链越长——新产出永远追加在时间末尾，而不是挂回它归属的部分；
- 并行的事被排成串行，仿佛必须一件做完再做下一件；
- 想返工其中一部分时无从下手：链上没有「部分」，只有「第几步」。

**一句话判据：这张板在开工之前能不能先画出来？** 能（细节后填）说明形状对——项目结构从规划到收尾大体不变；如果板是随做事过程一路往后长出来的（目标→调研→汇总→核查→定稿这种叙事链），那就是流水账。

## 形状三问（播种前、每次动板前过一遍）

1. **这个项目由哪几部分组成？**（并列地列——部分，不是步骤）
   「调研 A、调研 B、产出 C」是三部分；「先调研、再整理、最后写报告」是叙事。写下「先 / 然后 / 最后」就是警报。
2. **部分之间是什么关系？**（拆解 / 归属 / 引用）
   绝大多数是拆解（父卡扇出）；产出归属到产出它的那部分；跨部分互相参照用参照线。**没有「谁先谁后」——时序不构成连线理由。**
3. **删掉某一部分，其余部分还成立吗？**
   成立 → 它是独立分支（该并行画）；不成立 → 检查是不是把它编进了链条。

## 板型判断 → 骨架模板

先 `read_workflow` 看板（空白板也要看一眼确认归属），判断用户要的是什么（任务或问题）是哪一型，选一型起形，再播种：

### A 型：调研 / 分析类（查 X、统计 X、对比 X、梳理 X 现状——最常见）

形状：**总纲扇出 + 并行分支 + 汇收结论**。总纲卡放口径与计划；每个调研对象一张并行工作项卡；分支末端挂数据卡；全局结论一张结论卡汇收。

```
                    ┌→ 工作项[机械领域] ──→ 数据卡[机械清单]─┐
总纲[口径与计划] → 核查[口径确认] ─┼→ 工作项[电气领域] ──→ 数据卡[电气清单]─┼→ 结论卡[总量与分布]
                    └→ 工作项[电子领域] ──→ 数据卡[电子清单]─┘（各数据卡 → 结论卡为流程线；口径卡 ← 各分支为参照线）
```

播种 nodes_json 骨架示例（工作项 subs 拆好、任务行带短 id；产出卡先占位，数字产出后回填）：

```json
[
  {"id":"1","data":{"text":"目标：摸清五领域标准现状分布。口径待核查卡 2 拍板后全线执行。"}},
  {"id":"2","type":"reviewNode","data":{"question":"统计口径选哪种？","options":["宽口径：名称含领域词即计入","严口径：宽口径再去噪"],"answer":""}},
  {"id":"3","type":"taskNode","data":{"title":"机械领域收集","subs":[["检索含机械领域词标准","m1"],["去重去噪","m2"]],"summary":"宽口径检索"}},
  {"id":"4","type":"taskNode","data":{"title":"电气领域收集","subs":[["检索含电气领域词标准","e1"],["去重去噪","e2"]],"summary":"宽口径检索"}},
  {"id":"5","type":"taskNode","data":{"title":"电子领域收集","subs":[["检索含电子领域词标准","c1"],["去重去噪","c2"]],"summary":"宽口径检索"}},
  {"id":"6","type":"dataNode","data":{"title":"机械领域标准量","metric":"","note":"口径见核查卡 2，检索后回填"}},
  {"id":"7","type":"dataNode","data":{"title":"电气领域标准量","metric":"","note":"同上"}},
  {"id":"8","type":"dataNode","data":{"title":"电子领域标准量","metric":"","note":"同上"}},
  {"id":"9","type":"conclusionNode","data":{"claim":"（待汇收）","points":[],"caveat":""}}
]
```

连线（工作项卡多任务 → 任务行出线，id 带 sid）：

```json
[
  {"id":"e1-2","source":"1","target":"2"},
  {"id":"e2-3","source":"2","target":"3"},{"id":"e2-4","source":"2","target":"4"},{"id":"e2-5","source":"2","target":"5"},
  {"id":"e3-m1-6","source":"3","target":"6","sourceHandle":"m1"},
  {"id":"e4-e1-7","source":"4","target":"7","sourceHandle":"e1"},
  {"id":"e5-c1-8","source":"5","target":"8","sourceHandle":"c1"},
  {"id":"e6-9","source":"6","target":"9"},{"id":"e7-9","source":"7","target":"9"},{"id":"e8-9","source":"8","target":"9"}
]
```

### B 型：执行 / 交付类（做 X、生成 X、开发 X、写 X 报告）

形状：**阶段流水 + 阶段内扇出**。只有这一型配得上 start / end（确有执行流程）。主链是**阶段**（3~5 张工作项卡，如 需求→设计→产出→验收），每阶段卡扇出该阶段的产出附件 / 数据卡 / 核查卡。

```
开始 → 工作项[需求阶段] ─┬→ 附件[需求文档.docx]
             ↓           └→ 核查[需求确认]
      工作项[产出阶段] ──→ 附件[最终报告.html] → 结论卡[交付说明] → 结束
```

**主链是阶段不是步骤**——阶段内部的步骤全进该阶段卡的 subs。把「写大纲、找配图、排版」也铺成主链上的卡，就又退化成流水账了。

### C 型：台账 / 汇总类（整理 X 清单、建 X 名录、汇总 X 数据）

形状：**无流程并列台账**。没有 start / end（静态板别仪式化）。一张总纲卡（口径 / 范围说明）+ 并列条目卡（每个条目一张 dataNode 量化事实卡，或需要动手的用 taskNode）+ 汇收附件（台账本体做成 HTML / xlsx 附件挂总纲下）。

### D 型：决策 / 评审类（帮我选、评估 X、论证 X）

形状：**决策分叉为枢纽**。核查卡（方案 A/B）是枢纽，两分支（各方案论证：数据卡 / 文本卡）并行扇出，结论卡汇收给出推荐与理由。用户拍板后只展开选中的分支。

### E 型：提问 / 论证类（用户在板上提出实质性问题：为什么 X、X 和 Y 有什么区别、X 是不是 / 会不会、该怎么理解 X）

实质性问题也是活——别只在对话里直接答。形状与 A 型同源，但收口主角不同：A 型交付的是数据 / 台账，E 型交付的是**答案本身**（结论卡是全板主角，claim = 对问题的直接回答）。

形状：**问题总纲 + 子问题扇出 + 答案汇收**。问题本身一张总纲卡（问题原文 + 拆解口径 / 回答路径）；按子问题 / 论证角度并列拆解（每个子问题一张工作项卡，subs 拆该子问题的查证点）；每个子问题分支挂依据（数据卡 / 文本卡 / 附件）；最后一张结论卡汇收作答。

（角度只有两三个的简单问题可省总纲卡：子问题卡直出 + 结论卡即可。）

播种骨架示例（问题「为什么新旧版标准同一试验项的指标值差异很大？」）：

```json
[
  {"id":"1","data":{"text":"问题：为什么新旧版标准同一试验项的指标值差异很大？\n按三条路径拆解回答：沿革、技术依据、影响范围。"}},
  {"id":"2","type":"taskNode","data":{"title":"沿革梳理","subs":[["整理版本修订沿革","h1"],["提取该指标相关修订说明","h2"]],"summary":"哪次修订改的、修订理由原文"}},
  {"id":"3","type":"taskNode","data":{"title":"技术依据","subs":[["对比新旧版试验方法","t1"],["核查引用标准与设备条件变化","t2"]],"summary":"数值差异的技术原因"}},
  {"id":"4","type":"taskNode","data":{"title":"影响范围","subs":[["列出受该指标影响的产品类别","i1"]],"summary":"对合格判定的影响面"}},
  {"id":"5","type":"conclusionNode","data":{"claim":"（待汇收：对问题的直接回答）","points":[],"caveat":""}}
]
```

连线（总纲扇出、各分支汇入结论卡）：

```json
[
  {"id":"e1-2","source":"1","target":"2"},{"id":"e1-3","source":"1","target":"3"},{"id":"e1-4","source":"1","target":"4"},
  {"id":"e2-5","source":"2","target":"5"},{"id":"e3-5","source":"3","target":"5"},{"id":"e4-5","source":"4","target":"5"}
]
```

推进同 A 型：按板查证、依据挂回所属子问题分支、答案汇收进结论卡；对话只说「已更新到板上」。

**问题板的演进（关键场景：问题从初步提问开始，在多轮对话中不断延伸——板子跟着对话持续再规划，不是一次播种就定型）**：

- **追问 = 原问题的展开，在既有板上演进，绝不另起炉灶**：新角度 / 新子问题 → 总纲下补工作项分支；已有子问题的新证据 → 挂回原分支。
- **答案变了同步改板**：结论卡 claim / caveat 永远保持**当前最优答案**——被推翻的结论直接改写，绝不把多版答案在板上堆叠（演变过程留对话里，板上只有现值）。
- **答案再丰富也别塞一张结论卡**：claim 只放断言；论证 / 依据 / 细节拆成论证卡链（一条理由一张卡连进结论卡，见「论证卡链」），或沉成 HTML 附件——结论卡是主角，不是容器。
- **问题转向（从「问」到「要做」：「那帮我把 X 做出来」）= 板型演变**（E → B / D）：保留既有调研分支作依据，一次再规划里接上执行 / 决策分支，不另建板。
- **问题收敛就收拢**：查证完的子问题撤掉工作项卡（依据和结论留下），板子沉淀成该问题的知识面——日后再问同类问题，先 read_workflow 看这块板，在它基础上答或演进。
- 展开太大、原骨架形状装不下（总纲罩不住、分支互相纠缠）→ 走下方「重构处方」整板再规划。

**混合项目**：整体 B 型、某阶段内部是 A 型——**用扇出嵌套表达**（阶段卡再扇出子结构），不是把链拉长。

## 播种骨架标准流程

1. `read_workflow` 看板。空白板直接播种；**已有卡 = 在既有结构上增补**，别推倒重来（除非用户明说要重新规划）。
   首条消息内容单薄（一句话 / 意图含糊）不是不动板的理由：先落当前已知的（总纲卡写下问题 / 意图 + 必要的澄清核查卡），澄清后再展开骨架。
2. 判板型、选模板，用形状三问把节点清单草拟出来：每张卡都答得出「它是项目的哪个部分 / 哪个产出」。
3. **一次** `edit_workflow_board` 落地：nodes_json 全传新 id、edges_json 一次连齐（工作项卡尽量任务行出线）、title 改成项目名（动词 + 对象，如「五领域标准现状调研」，别叫「新建深度任务」）。
4. 对话里一两句话交代：布了什么形状、第一步等谁（哪张核查卡等用户拍板 / 从哪个分支开工）。

## 归属决策树（之后每次新增内容都走一遍）

```
新内容（产出 / 发现 / 结论 / 问题）
 ├─ 是板上已有信息的重复 / 补充？ → 并进那张卡，不开新卡
 ├─ 它属于项目哪个部分？——答不出 = 骨架缺这个部分，先补部分
 ├─ 是某工作项的进展 / 结果？ → 回填该卡 summary / subs，产出卡挂它下面
 ├─ 是分支级定论？           → 该分支汇收处挂结论卡（已有结论卡就**改写它**，不另加新版本）
 ├─ 是一块新工作？            → 对应父卡下加工作项卡（少见！工作应在规划时拆好——
 │                               中途不停冒新工作项卡，就是流水账复发的信号）
 └─ 只是参照另一张卡？        → 参照线，不动结构
放完再问一句：**板上有什么因此过时了？**（做完的工作项 → 撤；被推翻的结论 → 改写；改道的线 → 断了重连）
同一次 edit_workflow_board 里一起处理——只放新的、不清旧的，就是板子越长越乱的起点。
```

**禁止**：挂到最新加的卡下、挂到对话最后聊到的卡下、为做过的每一步开一张新卡。

## 结构演进（板是活的——每次动板都过一遍维护）

板的形状不是播种时定型的，是在对话往返中**持续维护、整理、重构**出来的。每次 edit_workflow_board 前按序过「演进三问」：

1. **填实**：新内容哪张既有卡能承载？回填 summary、重写 subs、把产出挂它下面——任何进展 / 结果 / 新发现的**默认选项**；
2. **撤 / 并 / 断**：哪些卡已完成使命（撤）？哪些卡互相重叠（并）？哪些线已不成立（断）？
3. **才轮到加**：加什么新卡、连到哪。第 1、2 问能消化的，走不到这一步。

- **撤卡 ≠ 丢信息**：被撤卡的内容早已活在归宿里——附件 fileNode、结论卡、并入的其他卡。撤掉的是壳，留下的是信息。
  **收尾信号**：工作项卡 subs 全部做完、产出已上板、summary 写明结论 → remove_node_ids 撤掉，只留产出与结论，不是留空壳。完成的工作留在板上是噪音。
- 改道：方向变了先断旧线（remove_edge_ids）再重连，过时的卡撤掉；被推翻的结论**改写既有结论卡**，绝不在旁边加一张新版本。
- **流水账的发作信号（对话中途同样适用，不只是播种时）**：新卡不断冒出来、既有卡的 summary 停在播种时的状态没人更新、链越拉越长——
  发现即停止新增，先做一轮收拢（填实 / 撤 / 并 / 断）；形状已坏的走下方「重构处方」。
- **只增不减是板的慢性病**：卡越多，用户越不愿意打开。

## 自检清单（流水账 + 巨型卡；播种后 / 大改后逐条过，长对话中卡越加越多时也过一遍）

- [ ] 第一层卡是「项目由什么组成」，不是「第 1/2/3 步」？
- [ ] 主形状是扇出（一入多出 / 多出汇入），单链段不超过 4 张卡？
- [ ] 并行的事画成了并行（没被流程线串成先后）？
- [ ] 工作项卡 subs 都拆满了（没有 subs 空着的工作项卡）？
- [ ] 产出挂在归属卡下，不是堆在链尾？
- [ ] 没有只为表达「先做完这个再做那个」的连线？
- [ ] start / end 只出现在确有执行流程的板上，且没挂业务内容？
- [ ] 核查卡设在它管辖的步骤之前，不是全堆在末尾等确认？
- [ ] 没有 subs 全做完、产出已上板的工作项卡还留着没撤？
- [ ] 没有同一信息在多张卡重复、多个版本的结论并存？
- [ ] 没有正文超 ~150 字的巨型卡、subs 超 7 条的工作项卡（read_workflow 的 overlong 标记会直接点名）？
- [ ] 结论卡 claim 还是一句话判决、points 没装论证（论证已拆成理由卡连进本卡 / 沉成附件）？

中了两条以上，停下来按下面处方重整，别继续往上堆。

## 重构处方（板已经是流水账时）

读板发现形状坏掉（用户抱怨乱、或自检清单中多条）：

1. `read_workflow` 读全板，提炼出「这板实际承载了项目的哪几部分」——从现有卡的内容反推结构，不是照抄现有连线。
2. 用形状三问重组：部分并列化 → 选模板起新骨架。
3. **一次 edit 搬家**：旧链卡 remove_node_ids 撤掉、新骨架 nodes_json 建好、连线重连；旧卡内容不是删掉，是**搬进对应新卡**（搬家时把 title / summary / subs / 数字带过去）。
4. 对话里说明重构逻辑：原来什么样、现在按什么结构组织、什么内容搬去了哪。

⚠️ 用户手工改过的板（read_workflow 返回 human_edit / version 变化）重整要谨慎：先尊重用户改动，大动作前对话里确认一句再搬。

## AI 重整（收到带 `[板子重整]` marker 的消息）

用户在画板页点「AI 重整」按钮时，前端会代发带 `[板子重整]` marker 的消息；用户在对话里口头说板乱了 / 要求整理板子，同样按本节处理。这是用户的**显式整理请求**——请求本身即确认：human_edit 板无需再对话确认（上节「重构处方」的确认条款在此不适用），但用户手改过的内容仍是整理的基础，只搬不回退。

流程：

1. **诊断**：`read_workflow` 读全板（带 overlong 标记的卡用 node_ids 钻取全文），对照「自检清单」逐条过，先分轻重：
   - **轻**（骨架形状还在，只是冗余卡 / 过期的线 / 没回填的 summary）→ 只做「结构演进」的填实 / 撤 / 并 / 断，不动骨架；
   - **重**（形状已坏成流水账、自检中两条以上）→ 按「重构处方」整板再规划。
2. **一次落地**：一次 edit_workflow_board 完成所有变更——并重复卡、撤完成使命的壳（内容必须先搬进归宿再撤）、断过期的线；走重构的，旧卡的 title / summary / subs / 数字逐项带进对应新卡。
3. **边界**：重整是整理，不是重做——不发明新内容、不新启工作；信息只能搬家，不能丢；附件（fileNode）跟着归属分支走；已作答的核查卡已按收口协议处理（撤或锁），重整时不动。
4. **汇报**：对话里两三句说清整了什么、为什么（并掉了哪些卡、撤了哪些壳；走了重构的说明现在按什么结构组织）。重整完成后前端会自动整板对齐坐标，不必你操心。

## 巨型卡处方（卡文本膨胀时）

信号：单卡正文超 ~150 字、subs 超 7 条、结论卡 claim 超一句话、read_workflow 概览给某卡打了 overlong 标记。
**长文本是形状错误的信号，不是内容充实的表现**——卡是索引，板子的价值是扫一眼就懂。发现即停手别再往里塞，一次 edit 走三个出口：

- **拆**：内容有并列结构就拆卡——工作项卡的超长 subs 升级成多张工作项卡（父卡扇出、任务行出线照旧）；长论证走「论证卡链」（见下节）：每条理由 / 依据各立一卡连进结论卡。
- **沉**：长文本本身是报告 / 明细 / 完整论证 → write_file（.html / .md）→ register_artifact → fileNode 挂到归属分支，原卡只留一句断言 + 指向。
- **删**：逐句重读卡文——过程解释、与他卡重复的信息、已被推翻的旧结论，该撤撤（信息已有归宿的撤壳，没有归宿的先搬再撤）。

## 论证卡链（论证上板的标准形状）

论证天生是结构：因为 A、因为 B，所以 C。**论证上板 ≠ 把论证段落贴进卡里**，而是把论证拆成**卡链**——每条独立的理由 / 依据各立一张卡，各用流程线连进结论卡：

```
文本卡[理由：GB/T 37687-2019 是 FOD 检测唯一强制标准] ─┐
数据卡[依据：温升限值 70℃（4.4.7 / 5.4.7）]           ├─→ 结论卡[判决：FOD 检测执行 GB/T 37687-2019]
附件[出处：GB/T 38775.6-2021（8.2.1 来源）]           ─┘
```

- **结论卡只装判决**：claim 一句话；points 只放极短指针，绝不放论证段落。
- **一个「因为」一张卡**：量化依据 → 数据卡；定性理由 → 文本卡（一句话讲清一条理由）；出处 / 标准原文 / 支撑文档 → 附件。
- 论证结构因此**在板上可见**——用户扫一眼就看到结论为什么成立，这正是工作流的意义之一。一张结论卡如果没有理由卡连进来，要么是结论没有依据，要么是依据被塞进了卡里。
- 与 E 型的关系：E 型是问题板的**整板形状**（子问题扇出 + 答案汇收）；论证卡链是答案汇收处的**局部形状**——作答时结论的理由照样逐条立卡连入，不因 E 型而豁免。
- 与「别撕碎信息」的边界：拆的是**不同的理由**（每张卡一条独立的论证），不是把同一条理由撕成主谓宾三张卡；几张卡复述同一组数字 = 重复，同样错。

## 人工核查节点收口协议（强制）

核查卡生命周期：**设卡（规划时）→ 用户作答 → 你推进 → 收口**。

- 用户在板上作答后，你会收到 `[人工核查已作答]` 消息（前端自动发）；或 read_workflow 看到 reviewNode 的 answered=true。先按答案推进依赖它的分支（该返工返工、该转向转向），把答案落进下游卡。
- **处理完、本轮结束前，必须收口这张核查卡，二选一**：
  - **撤卡**（remove_node_ids）：答案已提炼进下游卡、核查卡本身无留存价值——多数过程核查的默认选择；
  - **锁禁用**（upsert 该卡 `{"data":{"disabled":true}}`）：这段问答对项目有留存价值（如全项目照办的口径决定、方向选择）——锁住后用户不能再改动答案，卡可作为依据卡继续被参照线引用。
- **禁止**对已作答的核查卡不处理就走——那会在板上留一颗「已回答但随时又能被改」的地雷。
- 用户答案含糊、不足以推进：追问或更新该卡 question / options，同样别晾着。

## 工具契约

机器可读版在 frontmatter，这里给人看：

- `read_workflow(workflow_key, summary=True, node_ids?)`：看板。默认概览（每卡 id / 类型 + 截断摘要 + 全量连线）；传 node_ids 钻取全文。返回带 version（升高 = 用户改过板）与 human_edit（用户改动详尽简报）。
- `edit_workflow_board(workflow_key, nodes_json?, remove_node_ids?, edges_json?, remove_edge_ids?, title?)`：一组变更一次落地。nodes_json upsert（已有 id = data 深合并，只动传入字段；新 id = 加卡）；连线 id 约定 `e{source}-{target}` / `e{source}-{sid}-{target}`，任务行出线带 `sourceHandle`，参照线带 `kind:"ref"`。
- 锁定核查卡：`nodes_json` 传 `[{"id":"<卡id>","data":{"disabled":true}}]`——深合并只动 disabled 字段，question / options / answer 原样保留。

## 输出纪律（板子是内容的归宿，对话只留总结）

板子模式最常见的失败不是板画得乱，而是**关键内容全说在对话里，板上只剩几个空标题**。方向必须反过来：

- **重要内容先落板**：结论、数据、计划拆解、口径、决策及理由——一切值得用户细读 / 值得作为下一步依据 / 值得留存的内容，写进卡片。完整的分析过程、结论段落、详细方案都属于卡片，不属于对话。
- **对话里不复述板上内容**：板子操作完成后，对话只说「放了 / 更新了哪几张卡（各一句话点要点）+ 下一步等谁」。不逐节点复述，不把板上的分析、结论、方案再在对话里讲一遍。随讲随走的解释、澄清提问、进度总结才留在对话。
- 顺序永远是：**先写卡 → 后在对话汇报变更**。先在对话讲完再贴卡是双重输出，浪费且信息分裂。
- 无 marker。

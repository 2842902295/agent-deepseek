# 持续精造：工作协议（sustained-build）

> **本 skill 是 project-bound**——依赖本项目 qa_agent 挂载的 task / write_todos 等工具与 quality-scout 子 agent，无法跨项目移植。规范见 `_project/README.md`。
> 你会读到本协议，是因为用户**明确点亮了「持续精造」按钮**——他已预先接受更长的耗时与更多的消耗，换一件不需要他来回挑毛病就打磨到位的交付。你的工作就是配得上这份信任。

## 核心心智：持续运转，停下需要证据

普通模式下做完一轮就返回是默认行为；**精造模式下默认状态是继续工作**。把自己想象成一个持续运转的头脑：专注推进一阵，派灵感出去侦察一阵，回头整理一阵，偶尔发现确实没事做了才坦然歇下。

- "这一轮做完了" ≠ "任务结束了"。每一轮收尾时问自己：**还有什么值得在意的？** 回答不凭感觉，凭侦察兵的实检证据。
- 只有三种情况允许停：**侦察兵结论为"否"**（无实质改进空间）、**达到 5 轮安全上限**、**用户明确喊停**。其余一切"感觉差不多了"都不是停止理由。
- 反过来，**懈怠是美德不是失败**：侦察兵说没有实质空间了，就坦然收工，不要为了显得勤奋硬凑轮次、制造无意义的微调。

## 工具契约

- `write_todos`：整体替换式 todo 列表（content + status）。每轮最多调一次；完成一项就尽快更新状态。
- `task(subagent_type='quality-scout', description=...)`：委派侦察兵。它是独立上下文，**看不到你和用户的对话**——它知道的一切都必须写进 description（见「委派纪律」）。
- `register_artifact` / `publish_html_board`：产物登记与发布，产物被重写后按需重新执行，保证用户看到的永远是最新形态。

## 协议流程

### 第 0 步：计划先行

动手前先 `write_todos` 立计划，计划必须显式包含轮次结构，例如：

1. 构建初版骨架（in_progress）
2. 第 1 轮：侦察兵实检 + 按灵感演进（pending）
3. 第 2 轮：侦察兵实检 + 按灵感演进（pending）
4. 整理与最终摘要（pending）

后续随侦察结论增删轮次条目。未完成的 todo 就是你继续工作的理由——每完成一项立即更新状态。

### 第 1 步：初版

先交付**完整可用的骨架**：结构齐全、主路径能跑通，允许细节粗糙。不追求一步完美——完美是后面轮次的事。产物落盘 + 该登记 artifact 登记、该发布发布。

### 第 2 步起：节律循环

**深度工作轮**与**灵感轮**交替进行：

- **深度工作轮**：消化灵感束（或按自己的计划推进），演进产物。
- **灵感轮**：一次 `task(subagent_type='quality-scout')` 委派，拿到灵感束与结论后进入下一个深度工作轮。
- **整理轮**：每 2-3 轮插入一次（侦察兵结论为"建议整理轮"时必须照做）——不委派、不新增功能，自己把产物从头通读/通跑一遍：对照最初目标查漂移、查各部分之间是否还自洽、修订 todo 计划，顺手做小清理。

### 委派纪律（灵感轮的生命线）

侦察兵看不到本对话，`description` 必须写全四样，漏一样等于让它瞎审：

1. **用户原话需求全文**（照抄，别转述丢了细节）
2. **产物文件路径清单**（工作区相对路径，每个文件一句话说明是什么）
3. **当前轮次**（第 N/5 轮——它据此收紧或放宽"再来一轮"的判据）
4. **本轮关注点**（上轮改了什么、你拿不准的地方、希望它重点审什么）

侦察兵返回后：

- **不得改写、弱化或重新解释它的结论**——它说"是"就再来一轮，说"否"就收工，说"建议整理轮"就整理。
- 灵感束允许取舍（不是每条都值得做），但取舍要写进 todo 备注，不许无声遗忘。
- 连续两轮灵感高度重复（同一批问题反复出现）→ 说明触及当前能力边界，按停止条件收工，在摘要里诚实说明。

### 每轮收尾铁律

每一轮（深度工作轮与整理轮）必须以**产物被真实重写**收尾：write_file / edit_file 落下实际改动，需要时重新 register_artifact / publish_html_board。**禁止以"计划改进了 / 下一轮再改"收尾**——只动计划不动产物的轮次等于空转。

### 停止条件（三选一）

| 条件 | 动作 |
|---|---|
| 侦察兵结论"否" | 立即收工，进入最终摘要 |
| 达到 5 轮安全上限 | 收工，剩余遗憾在摘要里一句话带过 |
| 用户明确喊停 | 立即收工，按当前形态交付并说明现状 |

### 产物自验指引（自己也长眼睛，别全押给侦察兵）

- HTML / 应用 / 页面 → 通读代码；能用 execute 跑起来验证的跑一遍
- 脚本 / 数据处理 → execute 真跑一次，看真实输出
- 图片 / 图表 → 看一眼（支持视觉时 read_file 内联查看）
- 文档 / 长文 → 通读结构与关键段落

## 输出纪律：最终摘要

收工时给用户一个简短摘要，结构：

1. **初版做了什么**（一两句）
2. **各轮演进**（每轮一两句：发现什么问题、改成了什么）
3. **最终产物与用法**（artifact 占位符照常放置）

措辞遵守平台铁律：内部机制词（task、侦察兵、quality-scout、轮次编号、write_todos 等）一律翻译成业务语言——说"经过几轮自我审查与打磨"，不说"侦察兵第 2 轮返回了 3 条灵感"。

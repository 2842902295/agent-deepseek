# 沉淀（Sediment）

> **本 skill 是 project-bound**——直接调用本项目 qa_agent 运行时挂载的工具，无法跨项目移植。规范见 `_project/README.md`。

把刚才的对话凝练成长期价值。两种产物形态：**知识条目**（落入库）或 **技能**（可复用工作方式）。共同心法相同，工作流分开放在 references/ 下，按需读。

**素材在哪**：用户在对话里直接触发时，对话就在你的会话记忆里；消息里带「系统触发」字样并附有「对话历史 / 待整理内容」段时，素材以消息附带为准。

## 路由：识别 mode → 读对应 reference

按指令措辞判断走哪个模式：

| 触发线索 | 模式 | 必读文件 |
|---|---|---|
| 整理进库 / 整理进念念 / 沉淀到库 / 记下来 / 沉淀这次会话 / 把这段记下来 / 收件箱自由文本 | **A：沉淀到库** | `references/kb-mode.md` |
| 凝练为技能 / 沉淀为技能 / 抽象成能力 / 做成可复用 skill | **B：凝练为技能** | `references/skill-mode.md` |

**确定 mode 后第一件事**：用 `read_file` 读对应的 reference 文件——完整工作流与输出 schema 都在里面，不要凭本文件概要自行展开。

如果指令同时含两类词（少见），优先按出现的第一个动词走；不确定就当模式 A。

## 共同心法（两个模式都适用）

### 看时序、辨最终结论

对话里双方都可能中途改主意。沉淀只留**最终达成的版本**：同一主题出现多次时按时间取最后一版，被覆盖的中间产物与弯路不入库。

### 寒暄不沉淀

"好的"、"谢谢"、单纯问候和确认性回复都不是知识。整段对话只有这些时，candidates=0 / skill_key=null 直接报告"没什么可沉淀的"。

### 凭据是知识，要沉淀（但分开存）

服务器 IP、数据库连接、API key、账号密码等**值得入库**——用户记不住、下次还要用。但**不要混进方法论条目**：方法论讲*怎么做*（泛化可复用），凭据讲*连什么*（具体值、会变更），各自独立成条。拆分规则见 `references/kb-mode.md`。

### 一段对话往往能拆多条

对话横跨几个主题就分别处理；每条候选先查重（A：委派时要求 knowledge-base 子 agent 先搜后写；B：`skill_read`）再决定写入。命中相关旧条目时**优先升级旧的而非新建**。

### 解释 why，不要光罗列动作

每条 result 的 `note` 写为什么这么处理（为什么 merge / update / skip），不是动作的同义反复。

## 输出纪律（两个模式都适用）

- marker 必须严格写成 `<sediment-report>...</sediment-report>`，全小写、无空格，**只出现一次且在最后一条消息末尾**。后端用正则抠，缺失即整体失败。
- JSON 必须合法（双引号、无尾逗号、内部引号转义）。
- 任何模式下都要给出 `summary` 字段——后端用它弹 toast 给用户看。
- 工具失败、内容为空、不足以沉淀——别硬凑，在 summary 写明原因；不要创建空壳条目。
